Путь пользователя в системе контроля качества диалогов

AI оценивает каждый чат и звонок по настраиваемому чек-листу. Люди разбирают только исключения: спорные оценки, грубые ошибки, апелляции и калибровку. Документ описывает, кто работает в системе, что каждый видит и через какие шаги проходит.

01Что взяли у рынка

Посмотрели, как устроены QA-системы контакт-центров банков и финтеха: Verint, NICE, Zendesk QA, MaestroQA, Scorebuddy, отечественная речевая аналитика (BSS, U-BSS, T-Bank). У всех один и тот же каркас. Его и берём, а отличаемся объяснимостью и казахским языком.

04Вход и авторизация

ТЗ разрешает обойтись без логина. Но продукт для банка без ролей не продать, а апелляция «от имени оператора» требует понимать, кто действует. Поэтому делаем вход сразу, но простой, и закладываем путь к корпоративному SSO.

Для хакатона

  • Логин и пароль, пользователи создаются сидом
  • Сессия в httpOnly cookie, JWT на бэкенде, роль и группа внутри токена
  • На экране входа блок «Демо-доступ»: войти как QA, оператор, руководитель. Включается флагом окружения, в проде выключен
  • Переключение роли без выхода только в демо-режиме
  • Неактивность 30 минут → повторный вход с возвратом на ту же страницу

Для Freedom

  • SSO через Microsoft Entra ID (OIDC): Freedom работает на Dynamics 365, учётки уже там
  • Группы AD сопоставляются с ролями, руководитель — с группой операторов
  • Двухфакторная проверка на стороне SSO
  • Доступ к строкам на бэкенде: оператор физически не получает чужие диалоги
  • Неизменяемый журнал: вход, правка оценки, решение апелляции, публикация чек-листа

05Жизненный цикл оценки

Один диалог проходит через эти статусы. Статус виден в каждом списке и в шапке карточки, по нему строятся очереди.

stateDiagram-v2
  direction LR
  [*] --> Загружен
  Загружен --> Оценивается: запуск оценки
  Оценивается --> Ошибка: модель не ответила
  Ошибка --> Оценивается: повторить
  Оценивается --> Требует_проверки: уверенность ниже порога, грубая ошибка или случайная выборка
  Оценивается --> Опубликовано: всё уверенно
  Требует_проверки --> Опубликовано: QA подтвердил
  Опубликовано --> Ознакомлен: оператор открыл
  Ознакомлен --> Апелляция: оператор оспорил
  Апелляция --> Пересмотрено: принято или частично
  Апелляция --> Ознакомлен: отклонено
  Пересмотрено --> [*]
  Ознакомлен --> [*]: срок апелляции истёк

Смена версии чек-листа не меняет старые оценки. Переоценка создаёт новую оценку рядом, история хранит обе.

07Пути пользователя

Метка «ТЗ» отмечает сценарий, который жюри может попросить показать без подготовки. Выберите роль, чтобы увидеть только её пути.

Роль:
F1

Новые данные → оценка

ТЗ 5QA
  1. «Новые диалоги». Три способа: файл JSON в формате DEV, вставка JSON или ввод текстом построчно Клиент: … / Оператор: …. Жюри сможет вставить свой диалог прямо на защите.
  2. Проверка до отправки: нет реплик оператора, неизвестный говорящий, пустой текст. Язык и канал определяются автоматически, их можно поправить.
  3. Выбор чек-листа: по умолчанию активная версия для канала. Модель (облачная или локальная) в блоке «Дополнительно».
  4. «Оценить» → экран прогресса: состояние каждого диалога и каждого критерия. Можно уйти, по готовности придёт уведомление.
  5. Готово → таблица результатов пакета → клик открывает карточку диалога.
Если что-то не так: модель не ответила по критерию — только он помечен «Не оценён, повторить», остальное сохраняется. Все критерии N/A — итог «Не рассчитывается» с причиной, а не 0.
F2

Открыть диалог и понять оценку

ТЗ 4все роли
  1. Поиск по ID, оператору или фильтрам → карточка диалога.
  2. Справа итог, баллы по секциям, флаг грубой ошибки. Под итогом формула: «применимый вес 80, N/A перераспределён, коэффициент 1,25».
  3. Клик по критерию: ответ, обоснование, уверенность, номера реплик. Слева подсвечиваются эти реплики.
  4. У N/A всегда причина. Для звонков пометка: «Транскрипт распознан автоматически, ошибки распознавания не штрафуются».
  5. Внизу паспорт оценки: версия чек-листа, модель, дата, хэш промпта. История показывает все оценки этого диалога.
F3

Проверка в очереди

QA
  1. Очередь отсортирована по риску: грубые ошибки, затем апелляции, затем низкая уверенность, затем случайная выборка.
  2. В карточке спорные критерии раскрыты и помечены «Требует проверки».
  3. QA меняет ответ → балл пересчитывается сразу → без причины изменения подтвердить нельзя.
  4. «Подтвердить» публикует оценку оператору. «Следующий» открывает следующий диалог без возврата в список.
Важно: причины правок собираются в отчёт «Где AI ошибается». Он нужен руководителю QA, чтобы улучшать формулировки критериев.
F4

Все грубые ошибки

ТЗ 1QAКомплаенс
  1. Пункт меню «Грубые ошибки» со счётчиком открытых.
  2. В каждой строке: тип нарушения, причина одной фразой и цитата с номером реплики. Например: «Назвал баланс до подтверждения личности, #8».
  3. Фильтры: период, группа, тип, статус (новая, в работе, закрыта).
  4. Клик → карточка с раскрытым критерием 8. Комплаенс ставит статус и комментарий.
  5. Выгрузка списка в Excel.
F5

Апелляция от оператора

ТЗ 2ОператорQA
  1. Оператор → «Мои оценки» → диалог → «Ознакомлен».
  2. На критерии «Оспорить»: выбрать желаемый ответ, написать довод (обязательно), указать реплики. Можно оспорить несколько критериев сразу.
  3. Статус «Апелляция подана». Руководитель группы видит её и может отозвать без оснований.
  4. QA видит рядом довод, обоснование AI и переписку. Решение: принять, частично принять или отклонить, комментарий обязателен.
  5. Балл пересчитывается, в истории «было → стало». Оператор и QA получают уведомление.
Ограничения: одна апелляция на критерий, срок 5 рабочих дней с момента «Ознакомлен». Спор о грубой ошибке решает руководитель QA.
F6

Изменить чек-лист

ТЗ 3Рук. QA
  1. «Чек-листы» → активная версия → «Создать черновик».
  2. Изменить вес: сумма весов видна всегда, при сумме не 100 публикация недоступна. Отредактировать формулировку Да, Нет, N/A — это и есть инструкция для модели. Добавить критерий: название, секция, тип, шкала, N/A, вес.
  3. «Сравнить с текущей» — построчная разница.
  4. «Проверить на эталоне»: совпадение с разметкой было и стало.
  5. «Опубликовать» → предложение переоценить. Смена веса пересчитывается без модели, мгновенно и бесплатно. Смена формулировки переоценивает только этот критерий. Перед запуском видно число диалогов и стоимость.
  6. Итог: «Изменилось 12 оценок из 65», список изменённых. Старые оценки сохраняют метку прежней версии.
F7

Руководитель: от цифры к действию

Рук. группыДиректор
  1. Обзор качества: средний балл, тренд, покрытие, грубые ошибки, стоимость проверки.
  2. «Где теряем баллы» → клик по критерию → список диалогов с нарушением этого критерия.
  3. «Моя группа» → оператор → его слабый критерий → примеры диалогов.
  4. «Назначить коучинг»: тема — критерий, примеры прикрепляются автоматически.
Правило: каждая цифра кликабельна и ведёт к диалогам. Дашборд без следующего шага — типичный провал рынка.
F8

Калибровка

Рук. QAQA
  1. Руководитель QA выбирает 5–10 диалогов и участников.
  2. Каждый оценивает вслепую, не видя ответов AI и коллег.
  3. Сводная таблица: где мнения расходятся. AI показан как ещё один участник.
  4. Обсуждение → согласованный ответ становится эталоном. Неясные формулировки — кандидаты на правку чек-листа.
F9

Администрирование

Админ
  1. Пользователи: добавить, назначить роль и группу, заблокировать.
  2. Модель: облачная или локальная, порог уверенности, доля случайной выборки.
  3. Источники: подключение к Dynamics 365, телефонии, загрузка файлов.
  4. Журнал действий с фильтрами по пользователю и типу события.

08Апелляция подробно

Самый чувствительный путь: от него зависит, будут ли операторы доверять системе.

flowchart LR
  A["Оператор: Ознакомлен"] --> B{"Согласен?"}
  B -- да --> Z["Оценка закрыта"]
  B -- нет --> C["Оспорить критерии: новый ответ + довод"]
  C --> D{"Рук. группы: есть основание?"}
  D -- нет, отозвать --> Z
  D -- да или не смотрел 1 день --> E["QA: довод, обоснование AI, переписка"]
  E --> F{"Решение"}
  F -- принять --> G["Пересчёт балла, история было → стало"]
  F -- частично --> G
  F -- отклонить --> H["Комментарий оператору"]
  E -- грубая ошибка --> I["Рук. QA решает"]
  I --> F
  G --> N["Уведомление оператору и QA"]
  H --> N

12Дизайн и скиллы

Направление: спокойный рабочий инструмент. Нейтральные поверхности, один фирменный зелёный акцент. Цвет означает только статус: выполнено, нарушено, N/A, требует проверки. Таблицы плотные, цифры выровнены. Никаких маскотов, градиентов и игровых наград.

Taste Skill (tasteskill.dev)

Что это
Открытый скилл для Claude Code и других агентов. Библиотека из 247 сайтов, скрипт выдаёт три случайных дизайн-направления из двадцати, ищет фото в открытых коллекциях и проверяет страницу в браузере на 1440, 768 и 390 px.
Плюсы
Проверка своих скриншотов в браузере. С версии 2.1 есть отдельный режим для дашбордов и экранов приложений: тихие панели, выровненные цифры, цвет только для данных.
Минусы
Основной режим заточен под лендинги: «название монументом», «журнальная вёрстка», «финтех как стритвир». Для банка случайные направления — риск. Сборка 30–45 минут и сотни тысяч токенов, нужны Node 22 и Chrome.
Вывод
Брать частично Только режим inspect.mjs --app для проверки готовых экранов. Направление дизайна задаём сами через impeccable teach, без случайной выдачи.
